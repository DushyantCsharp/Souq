- [from workers] Perf note for the 500k import (scratch DB on the shared server, host load avg ~23 so absolute numbers are pessimistic): the batch's `INSERT INTO product_texts ... ON CONFLICT` takes ~4 s per 1k rows because `product_texts_touch_product` is a FOR EACH ROW trigger: every text row issues its own `UPDATE products SET version = version + 1`, i.e. ~2 extra full (non-HOT — `updated_at` is indexed, plus the GiST on category_path) product updates per new SKU, firing `products_sync_size` + `z_products_bump_version` each time. A statement-level variant (`AFTER INSERT OR UPDATE OR DELETE ... REFERENCING NEW TABLE AS n OLD TABLE AS o FOR EACH STATEMENT`, then one `UPDATE products SET version = version + 1 WHERE sku IN (<skus whose title/description changed>)`) would bump each product once per statement and cut the per-batch cost to one set-based UPDATE. Semantics for writers stay the same (my importer compares pre/post versions, it doesn't assume +2).
